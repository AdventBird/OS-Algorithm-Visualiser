The scenario: a big sale on an online shop

Thousands of customers place orders at the same moment. Each order needs payment, a stock update, an invoice and a delivery slot, and it competes for CPU time, memory and shared services. 1. The order queue: Producer–Consumer

In the shop: during a flash sale thousands of customers press “Buy” at once. Each click is handled by a web-server thread that drops the order into the order queue, which has only a few slots. Order-processing workers take orders out of the queue.

Producer = customer / web-server thread placing an orderConsumer = order-processing workerBounded buffer = the order queue (N slots)mutex = lock so two threads never write the same slotempty / full = free slots / orders waiting

Try it: place orders until the queue is full, then watch the next customer get blocked instead of the order being lost.

2. Which order next? CPU scheduling

In the shop: one worker (the CPU) faces many waiting orders, and the scheduler decides which one it handles next. Processing time is the work needed for payment, stock update and invoice. A customer’s waiting time is how long they wait before work on their order starts; turnaround is placing the order until it is finished.

FCFS = first order in the queue goes firstSJF = quickest order firstRound Robin = every order gets a short turn, so big orders cannot block small ones
Time slice

Which rule should the shop use?

SJF gives customers the shortest average wait but can starve big orders. Round Robin has a higher average but treats every customer fairly during the rush.

3. Sharing payment, stock and DB safely: Banker’s Algorithm

In the shop: every order holds some Payment Gateway slots, Inventory Service slots and DB connections, and asks for more as it progresses. Danger: Order A holds Inventory and waits for Payment while Order B holds Payment and waits for Inventory, so both wait forever (deadlock). The shop therefore grants a request only if every order can still finish afterwards.

Process = one customer orderAllocation = what it holds nowMax = the most it will needNeed = Max − HoldingAvailable = free right now

Try the two examples: one request is safe and granted, the other would risk deadlock and is denied.

4. Server memory for each order: Memory management

In the shop: an order being processed needs RAM for its cart, payment data and invoice. Server memory is split into five partitions, and the allocator chooses which partition each order goes into. Leftover space inside partitions is wasted, and small leftovers can add up to enough memory that still cannot fit a big order.

First Fit = first partition that is big enoughBest Fit = smallest partition that is big enoughWorst Fit = largest partitionFragmentation = free memory split into pieces too small to use

5. The full sale: all four working together

In the shop: customers place orders (producers) into the order queue; the worker (consumer) picks the next one using Round Robin; Banker’s Algorithm checks that its payment, stock and DB needs are safe; Best Fit gives it server RAM; it is processed and delivered; then everything is released and a queue slot frees up.

Stage glows = the part of the system working right now

Try “Flash-sale rush” (queue of 3) to see customers blocked and orders waiting for resources. A queue of 1 or 2 jams, because it fills with orders that cannot start yet.
